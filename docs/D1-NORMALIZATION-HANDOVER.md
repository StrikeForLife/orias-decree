**背包維持自由文字框，不做物品、數量、重量或裝備管理系統。**

本文件是實作任務交接，不代表 migration 已實作、正式 schema 已核對或正式部署已授權。請依 AGENTS.md 自主完成本機設計、實作、測試和 PR；正式 D1 修改、合併與部署由使用者另行處理。

## 最近核對的現有結構

2026-11-03 曾讀取 main 的 0001.sql、0002_owner_console.sql、worker.mjs、owner-admin.mjs 及 import-data.mjs；沒有直接讀取正式 D1。

- users、campaigns、access_grants：Google 身份、戰役、戰役內 player / dm 授權；無授權預設 reader。
- characters：id、campaign_id、owner_email、owner_user_id、sheet JSON、state JSON、version、edit_class、edit_spells。
- definitions：以 (kind,id) 為主鍵；kind 為 class / school / spell / weapon / beliefs / background，payload JSON、version、archived。

## 目標設計原則

具體表名及拆分粒度由最新程式與資料欄位盤點決定，不把下列方向視為已定稿 DDL：

- 角色名稱、等級、職業、法源道、出身、故事、法術位、六屬性等拆成有明確型別的欄位。
- 保留建角值、成長值與既有最終屬性的差別；舊角色缺少來源時保持缺失狀態，不猜測補值。
- 生命、臨時生命、意志拆成數值欄位；生命容許負值。
- 待結算傷口採適當關聯結構；保留原本順序、傷害及結算／止傷行為。
- 背包與一般私人筆記保留原文文字，可放角色私人資料表；場次筆記維持獨立紀錄。
- 典籍按職業、法源道、法術、武器、信仰、出身建立適當 typed tables；職業每級 perk、角色多信仰等建立適當關聯。
- 補上可由資料庫保證的外鍵、唯一條件及 CHECK；不能為套用新限制而靜默刪除或「修好」既有資料。
- 職業／法源道／法術／核心法術可能構成循環引用，需實際測試新增及編輯流程與插入順序。
- 維持典籍全站共用，不引入戰役專屬內容。
- 操作 request、歷史前後快照及稽核 JSON 可以保留；不要為去除 JSON 而改寫歷史。
- 盤點未知 payload / sheet / state 欄位，提供保留策略或明確阻擋報告，不只搬 UI 目前有顯示的欄位。
- 保留 ID、Unicode、換行、空字串、null / 缺失意義及既有內容；數值字串轉型須驗證，不能以 CAST 將非法字串默默轉 0。
- 不趁此調整衍生公式、重算舊角色 AC / HP / DC、增加物品系統、場次管理、規則引擎或重新設計 UI。

## 對外相容與安全

- 透過後端資料存取／映射層從新 schema 組裝現有 API 格式，前端與 owner console 的表單行為保持一致。
- 所有讀寫入口要一起盤點：登入認領、bootstrap、角色資源與撤銷、私人內容、場次筆記、建角、成長、重選、DM、owner CRUD、維護 CLI、本機初始化及備份驗證。
- 不只切換讀取而留下寫入舊 JSON；若分階段雙寫，需定義唯一真實來源、原子性、衝突處理及退出雙寫的條件。
- 保持 session / CSRF / Origin / Google 身份驗證、owner 與 DM 分離、啟用戰役範圍及未解鎖 perk 不傳送給玩家。
- 保持現行資料可見與修改範圍。現行 DM 可讀私人內容，場次筆記只有所屬玩家能修改；本次不更改此規則。
- 保持版本鎖、操作去重、引用保護、軟刪除及交易內檢查，不為通過測試而弱化保護。

## 遷移與發布

1. 採可驗證階段：新增 schema → 無損 backfill → 比對 → 切換讀寫 → 驗收；舊欄位／表的移除留待獨立後續版本，不在首次切換便刪除。
2. 已套用 migrations 不修改，新增下一個檔案；確認本機 SQLite 與 Cloudflare D1 支援的交易／DDL／外鍵行為，不假設兩者完全等價。
3. 搬移前報告無效 JSON、孤兒引用、重複關聯、未知欄位、無法解析的數值與排序；錯誤需阻擋或提出明確保留方式，不能丟資料。
4. 用隔離資料庫及虛構邊界資料演練。若使用者在本機提供正式備份，只能在私有、忽略追蹤的路徑處理，不提交或打印私人內容。
5. 正式資料尚未演練時，明確列為未完成驗證，不把虛構測試等同正式資料驗收。
6. 明確處理最後 backfill 至切換期間的寫入：採可測試的同步機制，或提供短暫維護／停止寫入流程，不能遺失期間變更。
7. 現有發布 preflight 要求 migration 名稱集合與選定版本完全相符；評估新增 schema 各階段、舊 Worker 與回退版本的實際部署順序。不可停用檢查或刪 migration 記錄繞過。
8. 回退須說明切換後新增資料如何保留；保留舊 JSON 但停止同步，不代表可直接回退舊 Worker。備份還原亦可能丟失備份後寫入，需清楚標示。
9. 交付使用者可執行的備份、唯讀 preflight、migration、驗證、發布及回退步驟；不要直接在正式 D1 套用。

## 驗收要求

- 資料：逐筆比對所有 ID、歸屬、文字、數值、空值、典籍欄位、關聯與軟刪除；不能只比較 COUNT。
- API：對相同虛構資料及身份，比較舊／新 schema 的 bootstrap、查詢和寫入結果。僅排除已明確解釋的隨機 ID / 時間差異，不排除真正內容差異。
- 身份：owner、各戰役 DM、角色擁有者、其他玩家、reader、未登入者；跨戰役與私人內容拒絕情境。
- 玩法：建角、負生命、臨時生命吸收、傷口順序與結算、止傷、豁免、祈禱、長休、撤銷、成長、DM 等級／法術位、重選許可與核心法術。
- 一致性：重試去重、stale version、並行修改、關聯移除／封存、owner 稽核與軟刪除恢復；多表寫入失敗不留下半完成狀態。
- 工具：從空庫啟動、既有庫升級、本機 migrations、備份驗證及受影響維護 CLI；不可重新匯入正式 seed。
- 執行目前 package scripts 定義的測試、format check、build；必要 UI 驗證保持既有介面可用。記錄實際完成與無法執行的項目。
